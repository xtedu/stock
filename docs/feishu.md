# 飞书是什么，以及本项目还能怎么用飞书

> 本文分两部分：
> **第一部分**讲清飞书这个产品是什么（面向"能给学生讲明白"的场景，含术语表与讲解要点）；
> **第二部分**盘点本项目现在用了飞书的哪些能力、**后续还有哪些地方可以用**（按落地成本分档，给出接入点与前置条件）。
> 具体「怎么绑定群机器人、怎么排查推送失败」见 [飞书通知绑定指南](feishu-notification.md)；
> 本项目与飞书无关的部分见 [技术方案](technical-design.md)。

# 第一部分：飞书是什么

## 1. 一句话定义

**飞书（Feishu / 国际版叫 Lark）是字节跳动自研的"一站式协作平台"**——把**沟通（IM）、文档、会议、日历、任务、审批、表格**装进一个工具里，

一句话概括它的产品逻辑：

```
飞书 = 企业微信（沟通） + Google Docs（文档） + Notion/Airtable（多维表格） + 日历 + 会议 + 审批 + 机器人开放平台
```

**讲解要点（这是学生最先要抓住的）**：飞书不是"聊天软件"，也不是"网盘"，
它的定位是**"企业的工作操作系统"**——把企业里"信息在哪儿、事怎么流转、人怎么协作"这三件事收进一个平台。

## 2. 和同类产品的差别在哪（学生最爱问）

| 维度 | 飞书（Feishu） | 企业微信（WeCom） | 钉钉（DingTalk） |
|---|---|---|---|
| 起家能力 | **文档 / 多维表格 / 协作深度** | 连接微信生态、客户触达 | 管理动作、考勤审批 |
| 长项 | 云文档多人实时协作、多维表格、知识库 | 与微信互通（外部联系人） | 管理强管控、流程数字化 |
| 开放平台 | 应用 / 机器人 / 卡片 / 事件订阅 / **群自定义机器人 Webhook** | 类似 | 类似 |
| 典型用户 | 互联网、研发密集型团队 | 零售、服务业、客户运营 | 制造业、传统企业 |

**讲解要点**：**"差异化"不等于"谁更好"**。
飞书强在**文档与协作的信息密度**（多人同屏编辑、多维表格当轻量系统、知识库沉淀），
本项目选它做通知通道，看中的是**机器人 + 卡片 + 开放平台**这一套"可编程"的能力。

## 3. 产品矩阵（飞书到底有哪些模块）

| 模块 | 是什么 | 一句话用在哪 |
|---|---|---|
| **IM（消息/群/机器人）** | 单聊、群聊、话题群、机器人 | **通知推送**、群内问答、告警 |
| **云文档** | 在线文档（Docx）、电子表格（Sheets）、多维表格（Base）、幻灯片、思维笔记 | 写报告、存数据、做看板 |
| **知识库（Wiki）** | 树状组织的文档空间 | 团队知识沉淀（本文档就该放这儿） |
| **日历** | 日程、忙闲、会议室 | 财报日/复盘会排期与提醒 |
| **视频会议 + 妙记** | 会议与"录音自动转纪要" | 投研会纪要、决策留痕 |
| **任务（Tasks）** | 待办、清单、指派协作人 | "今天要盯的票"清单 |
| **审批（Approval）** | 表单 + 流程审批 | 加仓/减仓决策留痕 |
| **OKR** | 目标与关键结果管理 | 团队目标对齐（本项目用不到） |
| **邮箱** | 企业邮箱 | 研报分发 |
| **开放平台** | 自建应用、机器人、事件订阅、卡片搭建 | **把上面一切能力接进自己的程序** |

**讲解要点**：给学生一个记忆锚点——**飞书 = "沟通" + "文档" + "流程" 三类能力 × 一个开放平台**。
本项目目前只用了其中**一格的 1%**（IM 里的群自定义机器人，单向发卡片）。

## 4. 三个必须讲透的概念（最容易混淆）

### 4.1 群自定义机器人 Webhook ≠ 开放平台自建应用

这是**学生第一次接触飞书必然混淆的点**，本项目正好踩在第一类上：

| 对比项 | 群自定义机器人 Webhook（**本项目用这个**） | 开放平台自建应用 |
|---|---|---|
| 本质 | 群里加一个"会说话的头像"，给它一个 URL 往里 POST | 在飞书开放平台注册一个"应用"，拿 `app_id/app_secret` |
| 能力方向 | **只能单向推送**（发消息到群） | **双向**：读文档、发消息、建任务、收回调 |
| 能否收到用户动作 | **不能**（没有事件订阅能力） | **能**（事件订阅 + 卡片回调） |
| 前置条件 | 只要一个飞书账号 + 一个群 | 需要企业/团队 + 管理员在开发者后台建应用 |
| 成本 | 复制一个 URL 填进 `.env` | 建应用 + 配权限（scopes）+ 授权 |

**讲解要点**：**"要不要能收用户的操作"是这两者的分水岭。**
只想"发通知" → Webhook 就够了；想"卡片上点按钮、群里的提问能回答" → 必须走自建应用。

### 4.2 消息类型：text / post / interactive（卡片）

飞书机器人发消息要指定 `msg_type`：

| msg_type | 形态 | 本项目 |
|---|---|---|
| `text` | 纯文本 | 未用 |
| `post` | 富文本（标题+段落） | 未用 |
| **`interactive`** | **消息卡片**（标题栏 + 内容块 + 按钮，结构化、美观） | **本项目用这个**（见 §7） |

**讲解要点**：为什么选卡片而不是文本？
—— 卡片有**结构**（标题/正文分区）、有**样式**（颜色标记）、**能放按钮**（未来做交互闭环的入口）。
本项目的提醒卡片标题是「`{股票名}({代码}) 低于区间下沿，低估区可关注`」，属于"一眼能看懂"的设计。

### 4.3 鉴权与 ID：open_id / tenant_access_token 是什么

| 概念 | 含义 | 学生要记住的一句话 |
|---|---|---|
| `app_id` / `app_secret` | 自建应用的身份证 | 换 `tenant_access_token` 用的 |
| `tenant_access_token` | **应用维度**的临时令牌（代表"这个应用"） | 后端定时任务（无用户在场）用它 |
| `user_access_token` | **用户维度**的令牌（代表"某个用户"） | 替用户读写他的文档时用 |
| `open_id` / `union_id` / `user_id` | 同一个用户的三套 ID | 给某人发消息前要先"把人找出来"（通讯录解析） |
| `chat_id` | 群的 ID | 给某个群发消息需要它 |

**讲解要点**：本项目**完全不涉及**这些——因为群自定义机器人 Webhook **不需要鉴权**（URL 本身就是凭据）。
一旦要用自建应用（读文档/建任务/收回调），**这一格就必须讲清**，否则会写出"用 `app_secret` 当 token 用"这类错误。

## 5. 术语表（飞书黑话速查）

| 术语 | 通俗解释 |
|---|---|
| 群机器人 | 群里一个"虚拟成员"，可发消息 |
| 自定义机器人 Webhook | 群机器人发出的一个"投递地址"，POST 内容即入群（**单向**） |
| 卡片 / interactive | 结构化消息（标题栏 + 内容 + 按钮），不是纯文本 |
| 卡片搭建工具 | 飞书提供的可视化卡片编辑器，产出 JSON |
| 开放平台 | 注册"应用"、配权限、订事件的地方 |
| 事件订阅 | 应用"订阅"飞书发生的事（有人发消息/点了卡片按钮），飞书回调你的服务器 |
| 多维表格 Base | 长得像 Excel、用起来像数据库的在线表（字段有类型、有视图、有仪表盘） |
| 妙记 | 会议录音自动转成可搜索的文字纪要 |
| 知识库 Wiki | 树状结构的团队文档空间（本文档的归宿） |
| 免登 / OAuth | 用户在飞书里打开你的网页应用，不用再输账号密码 |

**讲解要点**：**术语表本身就是一次测验**——让学生用一句话解释"自定义机器人 Webhook 和开放平台应用的区别"，
能答出来说明这一节真的懂了。

# 第二部分：本项目与飞书

## 6. 现状：本项目只用了飞书的一个能力

**唯一在用的**：群自定义机器人 Webhook，单向推送**结构化的提醒卡片**。

```
monitor.check_and_notify  （触发判定：price < zone_low，Redis 当日去重）
      └─▶ llm.summarize   （生成 ≤100 字解读）
            └─▶ notifier.notify(title, content, channels=['feishu'])
                  └─▶ notifier.send_feishu  （interactive 卡片 POST 到 Webhook）
                        └─▶ alert_logs     （落库，可回看）
```

| 环节 | 代码位置 |
|---|---|
| 触发判定 + 去重 | [monitor.py](../backend/app/services/monitor.py#L31-L86) |
| 卡片构造 + 签名 + 投递 | [notifier.send_feishu](../backend/app/services/notifier.py#L24-L45) |
| 多通道分发（飞书/Server酱/邮件） | [notifier.notify](../backend/app/services/notifier.py#L81-L88) |
| 配置项 | [config.py](../backend/app/config.py#L26-L27)（`FEISHU_WEBHOOK` / `FEISHU_SECRET`） |
| 绑定与排查 | [feishu-notification.md](feishu-notification.md) |

**一句话定位现状**：**"我们把飞书当成了一个'输出终端'——只往它里面推结果，不从它那儿取任何东西。"**

## 7. 后续可以用到飞书的地方（重点）

按**落地成本**分三档：A 档沿用现有 Webhook（零新增认证）、B 档需要开放平台自建应用（要企业管理权限）、C 档是深度集成。

### A 档：沿用现有 Webhook，改代码即可（成本最低，建议先做）

| # | 场景 | 用到的飞书能力 | 解决什么问题 | 本项目接入点 | 前置条件 |
|---|---|---|---|---|---|
| A1 | **每日收盘复盘卡片** | interactive 卡片（现成通道） | 现在只在"触发低估"时推消息，**没有"今天整体发生了什么"的日报** | 新增 16:20 后的汇总任务：读当日 `stock_pool` / `safety_zones` / `alert_logs`，拼一张卡片 | 无（复用 `send_feishu`） |
| A2 | **数据管道健康告警** | 同一个 Webhook（换一个群） | 同步失败/被限流/任务连续失败**目前无人知道**（只有日志） | 在 `_with_db` 与同步任务里捕获异常后 → `notifier.notify` 到运维群 | 无（多要一个群的 Webhook） |
| A3 | **通道分层** | 多个 Webhook | 提醒、告警、复盘混在一个群里会互相淹没 | 把 `alert_rules.channels` 从 `["feishu"]` 扩展为 `["feishu_alert"]` / `["feishu_ops"]` | 无（`CHANNELS` 字典加键） |
| A4 | **周报卡片** | 同上 | 一周的筛选变动、估值分位、资金流趋势汇总 | 周六基本面同步后追加一个汇总任务 | 无 |
| A5 | **大规模提醒的降噪** | 卡片 + 频率意识 | 群机器人**有频率限制**，一天几十条会刷屏 | 汇总成一条"今日低估清单"卡片（一卡多行），而不是一股多张卡 | 无（注意官方频率上限） |

**A 档的价值**：**不用申请任何东西，改一个 service 就能交付。** 讲项目时这是最好的"增量价值"演示。

### B 档：需要开放平台自建应用（价值最高，也是"飞书真正好玩"的地方）

> 前置条件统一为：**企业/团队 + 管理员在开放平台创建自建应用 + 配置权限（scopes）+ 授权**。
> 本项目的开发环境已具备飞书系列技能（见 §8），可直接调用做端到端验证。

| # | 场景 | 用到的飞书能力 | 解决什么问题 | 本项目接入点 | 前置条件 |
|---|---|---|---|---|---|
| B1 | **多维表格做「股池看板」** | 多维表格 Base（记录读写） | 现在看股池必须打开本项目 H5；团队/同学**在飞书里就能看**，还能筛选、做视图、做仪表盘 | 每日 16:15 后把 `stock_pool`（得分/ROE/CAGR/PE 分位）+ `safety_zones`（区间/三态/预警线）同步到一张 Base 表 | 自建应用 + Base 读写权限 |
| B2 | **提醒记录同步到 Base** | Base | `alert_logs` 现在只能在项目页面看，**无法协作**（谁跟进了、结论是驳回还是采纳） | 推送成功时同步一行到"提醒跟进表"，加"跟进人/结论"字段 | 同上 |
| B3 | **对比分析秒变表格** | 电子表格 Sheets / Base | 选 2-8 只股票做对比后，结果**只能在本项目页面看**，无法直接发给别人/做二次编辑 | `POST /api/compare/analyze` 落库后，把 `items` 导出到一张 Sheets/Base | 自建应用 + 表格权限 |
| B4 | **自动生成日报/周报文档** | 云文档 Docx | 复盘内容目前散在日志和数据库里，**没有可交付的文档** | 把"候选池变动 + 触发清单 + AI 总体结论"渲染成一篇 Docx，链接推群 | 自建应用 + 文档读写权限 |
| B5 | **卡片按钮闭环（最能体现"双向"）** | interactive 卡片 + 事件订阅（card.action.trigger） | 现在的卡片**只能看**。想做的动作（"这只加入关注""今天不用管"）只能去本项目页面点 | 卡片加三个按钮 → 回调打到后端 → 写 `alert_rules`（加入关注 = 建规则）或写忽略标记 | 自建应用 + **事件订阅 + 回调地址** |
| B6 | **群内问答机器人** | IM 消息 + 事件订阅 | 想查"600519 现在贵不贵"必须开网页。群里 `@机器人 /区间 600519` 直接回 | 收到消息事件 → 调本项目 `GET /api/zones/{code}` → 回卡片 | 自建应用 + 消息事件 + 读消息权限 |
| B7 | **自动建任务** | 任务 Tasks | 触发提醒后**没有人负责**，"看了一眼就过去了" | 每次触发低估 → 建一条任务「复盘 {name}({code})」，指派给自己 | 自建应用 + 任务权限 |
| B8 | **财报/事件日历** | 日历 Calendar | 财报披露日、股东大会日靠人记，**容易错过** | 财报日入库后建日程（提前 1 天提醒） | 自建应用 + 日历权限 |
| B9 | **决策审批留痕** | 审批 Approval | 模拟盘/小组演练里，"谁在什么依据下决定买"没有记录 | 小组把"计划加仓 {code}"发起审批，附当前区间/资金流/评分 | 自建应用 + 审批权限（或管理员建审批定义） |
| B10 | **会议纪要回流** | 妙记 Minutes / 会议 | 投研会结论停在会议里，没进数据库 | 会议结束后取纪要 → 人工确认后写入项目 | 自建应用 + 妙记权限 |
| B11 | **研报邮件分发** | 邮箱 | 报告只存在本地 | 生成的 Docx 走邮件发送 | 自建应用 + 邮箱权限 |
| B12 | **文档沉淀进知识库** | 知识库 Wiki | [algorithm.md](algorithm.md)、[scheduler.md](scheduler.md) 只躺在仓库里，**新人看不到** | 把 docs/ 导入 Wiki，形成"团队知识库" | 自建应用 + Wiki 权限 |

### C 档：深度集成（当作演进方向讲，不必马上做）

| # | 场景 | 说明 |
|---|---|---|
| C1 | **Base 作为反向数据源** | 在飞书 Base 里维护"自选股 + 关注权重"，本项目反过来**读**它作为筛选输入（双向数据流） |
| C2 | **H5 免登 + 工作台应用** | 把本项目 H5 注册成飞书应用，从工作台直接打开、免账号密码（OAuth 扫码登录） |
| C3 | **条件化实时推送** | 不只推"低于下沿"，还可推"跌破预警线""资金流突变为大额净流入"（口径见 [algorithm.md §5](algorithm.md)） |
| C4 | **多维表格当配置中心** | 权重（35/15/15/15/20）、安全区间带宽、PE 分位阈值……**在 Base 里改，不用改代码重启** |

**讲解要点（这部分最容易讲出彩的地方）**：
**同一条数据，飞书能给出四种"形态"——卡片（看）、表格（查/筛）、文档（交付）、任务（做）。**
把它讲成"**同一个后端数据的不同输出终端**"，学生立刻能理解为什么要用飞书：

```
                     ┌─▶ 卡片（IM）     看：一眼知道发生了什么
本项目数据 ──────────┼─▶ 表格（Base）   查：团队筛选、协作、仪表盘
(stock_pool/         ├─▶ 文档（Docx）   交：可以直接交付的报告
 alert_logs/...)     ├─▶ 任务（Tasks）  做：有人负责推进
                     └─▶ 审批（Approval）留痕：决策可追溯
```

### 落地优先级建议（三条）

| 优先级 | 做什么 | 为什么先做这个 |
|---|---|---|
| **1（零成本）** | A1 收盘复盘卡片 + A2 运维告警 | 复用现有 Webhook，不改任何认证，**当天就能交付** |
| **2（低成本高价值）** | B1 股池 → 多维表格看板 | 飞书最独特的能力（Base），**一次同步换来"飞书里能看能用"** |
| **3（体现双向）** | B5 卡片按钮闭环 + B6 群内问答 | 从"单向输出终端"升级成"双向交互入口"，是讲项目时最有说服力的升级 |

## 8. 本环境可直接调用的飞书能力（落地抓手）

要让上面某一条真正跑起来，本项目**开发环境已挂载以下飞书能力**，可直接调用做端到端验证，无需自己写 SDK：

| 想落地的场景 | 可用能力 |
|---|---|
| A 档（发消息/卡片） | `lark-im`（收发消息、管理群、卡片） |
| B1/B2 多维表格看板 | `lark-base`（建表、字段、记录、视图、仪表盘） |
| B3 导出表格 | `lark-sheets`（电子表格读写与美化）、`lark-drive`（上传下载） |
| B4/B12 文档与知识库 | `lark-doc`（创建编辑文档）、`lark-wiki`（知识空间与节点） |
| B5/B6 双向交互 | `lark-im`（卡片、卡片按钮回调监听） |
| B7 自动建任务 | `lark-task` |
| B8 日历提醒 | `lark-calendar` |
| B9 审批留痕 | `lark-approval` |
| B10 会议纪要 | `lark-meeting`（纪要/妙记/逐字稿） |
| B11 邮件分发 | `lark-mail` |
| 认证与权限排错 | `lark-shared`（登录/授权/权限域） |

**注意区分两个世界**（本项目最大的认知坑）：
- **现状**（`send_feishu`）走的是**群自定义机器人 Webhook**，与上面这些技能**不是同一套体系**；
- 上面这些技能走的是**开放平台 + 授权**，需要先完成 `lark-shared` 的登录/授权。

## 9. 常见问答（学生版）

| 提问 | 回答要点 |
|---|---|
| 用飞书要钱吗？要企业认证吗？ | 用**群自定义机器人 Webhook 不要**（个人账号 + 一个群即可，本项目现状）；用**开放平台自建应用**需要企业/团队与管理员授权 |
| 群机器人是个"应用"吗？ | 不是。它是群里的一个虚拟成员，**没有应用身份、不能收回调**；绑一个 URL 就能往里发消息 |
| 为什么卡片不是文本？ | 卡片是**结构化**消息（标题/分区/按钮/颜色），好看且**为未来的交互按钮留了口子** |
| 卡片上能加按钮吗？加了能收到点击吗？ | 卡片**可以**画按钮；但**群自定义机器人收不到点击事件**——要收回调必须走自建应用 + 事件订阅 |
| 为什么 Webhook 泄露很危险？ | **URL 本身就是凭据**（无需鉴权即可发消息）→ 不能提交进仓库、不能贴到公开场合（`.env` 已在 `.gitignore`） |
| 一天能发多少条？ | 群机器人**有频率限制**（官方有每分钟上限）→ 提醒要**汇总成清单卡片**而不是一股多张卡 |
| 为什么"低于下沿"只推一次？ | Redis `SET NX EX 86400` 当日去重（[monitor.py](../backend/app/services/monitor.py#L25-L28)），避免同一只票反复打扰 |
| 推送失败了怎么知道？ | 飞书可能**HTTP 200 但业务码非 0**，所以代码判定 `data.get("code") == 0`，非 0 记 warning 返回 `False`（见 [feishu-notification.md §6](feishu-notification.md)） |
| 多维表格和 Excel 有什么区别？ | Base 有**字段类型、多视图（看板/日历/仪表盘）、权限与协作、还能被 API 读写**——它更像"轻量数据库"而不是表格 |
| 为什么说飞书适合这个项目？ | 因为项目的产出天然是"**要给人看的结论**"：提醒（卡片）、看板（表格）、报告（文档）、待办（任务）——飞书把四种形态都备好了 |

## 10. 十分钟讲解提纲

| 时长 | 内容 | 一句话开场 |
|---|---|---|
| 1 min | 一句话定义 + 产品矩阵 | "飞书不是聊天软件，是**企业的工作操作系统**：沟通、文档、流程三件事装在一起。" |
| 2 min | 产品矩阵表 + 与企微/钉钉的差别 | "它最强的是文档和多维表格，不是管控。" |
| 2 min | **两个体系的分水岭**（重点） | "只想发通知 → 群机器人 Webhook；想收回用户的动作 → 必须走开放平台自建应用。" |
| 1 min | 本项目现状：只用了 1% | "我们只把它当**输出终端**：单向推卡片，从不往回取数据。" |
| 3 min | **后续可用点：一张数据的四种形态**（重点） | "同一份股池数据，飞书能变成卡片、表格、文档、任务——分别是'看、查、交、做'。" |
| 1 min | 落地优先级 | "零成本的日报卡片先做，再看板，最后做卡片按钮形成闭环。" |

**讲"两个体系的分水岭"和"一张数据的四种形态"时，一定要举本项目的具体例子**——
"提醒卡片只有标题和文字，加个「加入关注」按钮就必须申请自建应用" 比背概念好懂得多。
